# خطة إصدار Android وiOS

## استراتيجية المنتج
استخدام Flutter لتوحيد واجهة التطبيق ومنطق العرض، مع إعدادات بناء مستقلة لكل منصة. لا يعني ذلك أن إصدار المتجرين ينتج تلقائياً؛ لكل متجر متطلبات توقيع ومراجعة ونشر مستقلة.

## Android
- إنشاء مشروع Android بواسطة `flutter create . --platforms=android,ios`.
- ضبط `applicationId` النهائي واسم التطبيق وأيقونته ونسخة SDK المستهدفة وفق متطلبات Google Play السارية وقت النشر.
- اختبار أذونات الموقع عند الاستخدام فقط، وحالات رفض الإذن، وعدم توفر GPS.
- توقيع نسخة release بمفتاح مملوك للمشروع ومحفوظ خارج Git.
- اختبار APK على أجهزة فعلية، ورفع AAB إلى مسار الاختبار الداخلي في Play Console.

## Apple iOS
- يتطلب macOS ونسخة Xcode متوافقة مع إصدار Flutter المستعمل. لا يمكن إنتاج ملف iOS موقع للنشر من Windows أو Linux وحدهما.
- ضبط Bundle Identifier وTeam وSigning في Xcode.
- إضافة نصوص توضيح سبب طلب الموقع وأي أذونات أخرى في Info.plist عند الحاجة فقط.
- اختبار iPhone وiPad، وأحجام الشاشات، وVoiceOver، واللغتين وRTL.
- إنشاء Archive ورفعه إلى App Store Connect ثم TestFlight، وبعد الاختبار إرسال التطبيق لمراجعة App Store.

## معايير الجودة قبل الإصدار
- لا تظهر منشأة أو طبيب بعلامة «تم التحقق» دون مستندات ومراجعة موثقة.
- ساعات العمل لا تُعرض على أنها موعد حجز مؤكد.
- توضيح أن التغطية الجغرافية تختلف حسب البلد.
- طلب الموقع بعد توضيح فائدته، وتوفير البحث اليدوي عند الرفض.
- عدم جمع معلومات المرضى أو السجلات الصحية ضمن دليل المنشآت.
- توفير سياسة خصوصية وروابط دعم وآلية للإبلاغ عن بيانات خاطئة.
- اختبارات تلقائية للترجمة والتنقل وحالات انقطاع الشبكة والأخطاء.

## بوابة قبول الإصدار
لا يعتبر الإصدار جاهزاً حتى تنجح أو تُراجع: `flutter analyze` و`flutter test`، واختبارات أجهزة فعلية، واختبار API وقاعدة البيانات، ومراجعة الخصوصية والأمان، ثم التوقيع والنشر التجريبي لكل منصة.
